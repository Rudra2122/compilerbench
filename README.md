# CompilerBench: A PyTorch Model Through Every Compilation Path, Down to a Snapdragon NPU

## Overview

CompilerBench pushes PyTorch models through the main compilation and deployment paths and checks every stage against a reference, rather than trusting the tool that produced it.

- **v2 (current): MobileNetV2, quantized and deployed.** Static int8 post-training quantization with calibration (per-tensor vs per-channel, three range estimators), scored for real task accuracy. ExecuTorch lowering, portable kernels vs the XNNPACK delegate. On-device profiling and inference on a Snapdragon phone's Hexagon NPU through Qualcomm AI Hub.
- **v1: TinyCNN through every compiler entry point.** `torch.export`, `torch.compile`, ONNX, TVM Relax (operator fusion shown by IR diff), ExecuTorch and LiteRT, each verified against PyTorch. Kept in [`v1_tinycnn/`](v1_tinycnn/).

## What changed from v1 to v2, and why

| v1 | Problem | v2 |
|---|---|---|
| Toy CNN, 0.05 ms per inference | At the level of per-call overhead, so latency ratios measured Python overhead, not kernels | MobileNetV2 (3.5M params, ~300 MFLOPs), a real mobile model |
| `quantize_dynamic` | Dynamic quantization is aimed at Linear/LSTM models. On a CNN, ORT turns every Conv into `DynamicQuantizeLinear` + `ConvInteger`, which was the 6.8x slowdown | Static QDQ PTQ with calibration: per-tensor vs **per-channel**, MinMax / Percentile / Entropy |
| Output drift only | Logit drift is not task accuracy | Top-1 on 3,925 held-out images, Δ vs fp32, prediction agreement with fp32 |
| ExecuTorch `to_edge()` with no partitioner | Ran entirely on portable reference kernels, which was never stated | Portable vs **XNNPACK fp32** vs **XNNPACK int8**, with a delegation table |
| CPU only | No target hardware | **Qualcomm AI Hub**: compile, quantize, profile and run inference on a Snapdragon phone, with per-layer NPU/CPU placement |

Design rationale for every quantization choice (static vs dynamic, symmetric vs asymmetric, granularity, calibration, PTQ vs QAT) is in **[docs/QUANTIZATION.md](docs/QUANTIZATION.md)**.

## v2 pipeline

**Data** (`data_prep.py`): [Imagenette](https://github.com/fastai/imagenette), 10 ImageNet classes. Each class maps to its ImageNet index, so the pretrained **1000-class** head is scored unchanged: a hit requires the 1000-way argmax to be correct. Calibration uses 256 class-balanced *train* images. Evaluation uses all 3,925 *val* images. Images are preprocessed once and cached, so every stage sees identical pixels.

**Stage 2a: fp32 reference + ONNX** (`stage2a_onnx.py`). Produces the PyTorch fp32 logits every later stage is compared against, then exports to ONNX with the `torch.export`-based exporter, which folds all 52 BatchNorms into their Convs. The export is verified on the full eval set.

**Stage 3: int8 PTQ, ONNX Runtime** (`stage3_quantize.py`). Six variants: fp32, dynamic (the v1 method, kept as the baseline), static per-tensor MinMax, and static per-channel with MinMax, Percentile and Entropy calibration. For each variant the stage records top-1, Δ vs fp32, agreement with fp32, latency (p50/p90, 1 thread and all threads), model size, and **the op types ORT actually executes after graph optimization**. That last one shows *why* each variant is fast or slow instead of asserting it. The stage also measures per-channel weight-range spread on the BN-folded weights, which is the mechanism behind per-tensor's accuracy loss on MobileNetV2.

**Stage 4a: ExecuTorch** (`stage4a_executorch.py`). Builds three `.pte` programs: portable kernels (what v1 did), XNNPACK fp32, and XNNPACK int8 (PT2E `XNNPACKQuantizer`, per-channel, same calibration set). For each: which ops were delegated and which fell back, latency, accuracy, and a lowering check against the program's *own* PyTorch reference, so lowering bugs and quantization error are measured separately.

**Stage 5: on-device, Snapdragon via Qualcomm AI Hub** (`stage5_aihub.py`). Compiles the same model for a hosted Snapdragon phone as TFLite fp32, QNN fp32 and QNN int8. The int8 model comes from AI Hub's quantize job fed *this repo's* calibration images. It is profiled on-device (latency, memory, per-layer compute unit: NPU / GPU / CPU) and run on 200 eval images **on the phone** for on-target top-1. Every number links to the AI Hub job that produced it.

## Reproduce

```bash
python3.11 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

make all        # data download (~330 MB), stages 2a, 3, 4a, then report -> README
                # stage 4a portable kernels are slow by design; they're scored on 100 images

# on-device stage (needs a Qualcomm ID + API token from aihub.qualcomm.com -> Settings)
qai-hub configure --api_token <TOKEN>
python stage5_aihub.py --list-devices
make aihub      # default device: "Samsung Galaxy S24 (Family)"; override with --device

make smoke      # whole local pipeline on random weights + random images, no downloads (checks plumbing only)
```

ExecuTorch releases are built against one specific torch version; `requirements.txt` pins a matching pair (torch 2.14.0 / executorch 1.5.1). Change them together or the import fails (see v1 Engineering Note 4).

## Limitations

- PTQ only: no QAT, cross-layer equalization, bias correction or AdaRound. See [docs/QUANTIZATION.md §6–7](docs/QUANTIZATION.md) for where each would come in.
- Accuracy is on Imagenette (10 ImageNet classes, 1000-way head), so read the Δ vs fp32 rather than the absolute top-1.
- Laptop latency is Python-binding wall clock at batch 1. On-device latency is AI Hub's profiler measurement.
- The on-device int8 model is quantized by AI Hub's quantizer, not ORT's, so stage 3 and stage 5 int8 rows are different quantizers on the same calibration data.
- TVM (v1) still targets generic `llvm` CPU only.

# v1: TinyCNN through every compilation path

The original project, unchanged apart from paths. Run its scripts from inside `v1_tinycnn/` with `v1_tinycnn/requirements-v1.txt`. Its int8 result was superseded by v2 stage 3.

### v1 pipeline

**Stage 1: torch.export and torch.compile.** The model is exported with `torch.export`, producing an `ExportedProgram` whose FX graph and ATen ops are dumped directly. The same model is separately run through `torch.compile` with a custom backend that intercepts the captured FX graph before returning it unmodified, so the ops seen by both compilation entry points can be compared directly.

**Stage 2a: ONNX export.** The model is exported to ONNX and run through ONNXRuntime, with output diffed against the original PyTorch model for correctness.

**Stage 2b: TVM Relax.** The ONNX graph is imported into TVM's current IR (Relax, the successor to the older Relay IR, which is not present in current TVM releases). `LegalizeOps`, `AnnotateTIROpPattern`, `FuseOps`, and `FuseTIR` are run in sequence, with the IR dumped before and after to confirm the fusion and shape-inference passes actually changed the graph rather than assuming they did.

**Stage 3: int8 quantization.** The ONNX model is quantized to int8 with ONNX Runtime's dynamic quantization tool, then benchmarked against the fp32 version for latency and output drift.

**Stage 4a: ExecuTorch.** The exported program is lowered through ExecuTorch's edge dialect and compiled to a `.pte` artifact, then loaded back into ExecuTorch's own runtime and checked against the PyTorch output.

**Stage 4b: LiteRT.** The ONNX model is converted to TFLite/LiteRT format via `onnx2tf`, verified independently against PyTorch output rather than relying only on the converter's own internal check.

The TVM result is the strongest evidence in this project. Operator fusion is not stated as a claim, it is shown directly by diffing the IR before and after the pass runs, and the fused kernel is visible by name in the output.

### Op Count Reconciliation

`torch.export` (14 ops) and `torch.compile` (12 ops) do not report the same count for the same model, and the difference is fully explained rather than left as noise. Both traces agree exactly on conv2d, batch_norm, relu, max_pool2d, and linear. The 2-op gap is two `getitem` calls present only on the export side: `torch.export`'s decomposition lowers BatchNorm to `aten._native_batch_norm_legit_no_training`, which returns a 3-tuple, requiring a `getitem` to extract the output tensor. `torch.compile`'s trace keeps `batch_norm` as a single higher-level call and never produces that tuple, so no `getitem` is needed. Same computation, different internal bookkeeping at the two entry points.

### v1 engineering notes

Four version-dependent issues were found and resolved during this project. Each is documented with the actual error, its root cause, and the fix applied, rather than summarized as "some issues came up."

#### 1. Cross-stage comparisons were silently invalid due to unseeded weights

**Symptom:** PyTorch vs. LiteRT output comparison showed a large, unexplained divergence (max abs diff of 0.386), suggesting a broken conversion.

**Cause:** The model was instantiated fresh in every stage script with no fixed seed. Since each stage runs as a separate process, every script was creating a *different* randomly initialized model. The divergence was two unrelated random models being diffed against each other, not a conversion bug.

**Fix:** Seed with `torch.manual_seed(42)` and persist weights to a shared checkpoint file (`tinycnn_weights.pt`) that every stage loads, guaranteeing all comparisons run against the same model.

#### 2. torch.compile's custom backend reported 1 op instead of ~12

**Symptom:** A backend hook counting `call_function` nodes reported only 1 intercepted op, versus 14 ATen ops from `torch.export` on the same model.

**Cause:** On torch 2.4.1, `torch.compile`'s default trace leaves each `nn.Module` call (`self.conv1(x)`, `self.bn1(x)`, etc.) as an opaque `call_module` node rather than inlining it into ATen-level `call_function` ops. A hook that only checks for `call_function` misses nearly the entire graph.

**Fix:** Set `torch._dynamo.config.inline_inbuilt_nn_modules = True` before calling `torch.compile`, forcing the same ATen-level inlining that `torch.export` already performs by default. Op count went from 1 to 12, correctly reconciled against the export side (see Op Count Reconciliation below).

#### 3. ONNX export failed with "Unsupported FX nodes"

**Symptom:**
```
torch.onnx.OnnxExporterError: Failed to export the model to ONNX.
Unsupported FX nodes: {'call_function': ['aten.convolution.default',
'aten.max_pool2d_with_indices.default', ...]}
```

**Cause:** `torch.onnx.export(..., dynamo=True)` on torch 2.4.1 routes through `torch.onnx.dynamo_export`, an early-stage prototype exporter at that version that does not yet support ordinary ops like convolution and max pooling.

**Fix:** Use `dynamo=False`, the mature, long-standing TorchScript-based exporter. Exported the same model without modification and matched PyTorch output to ~1e-7.

**Update (v2):** on torch 2.14 the `dynamo=True` exporter handles MobileNetV2 without issue and constant-folds all 52 BatchNorms into their Convs. v2 uses it.

#### 4. ExecuTorch import chain failed across three separate, stacked causes

**Symptom (first):**
```
ImportError: cannot import name '_common_getitem_elimination_pass'
from 'torch.export.exported_program'
```

**Cause:** The current ExecuTorch release on PyPI requires `torch>=2.9.0`; the installed torch was `2.4.1`.

**Fix:** Installed `executorch==0.3.0`, the release pinned to `torch==2.4.0`, using `pip install --no-deps` to avoid a forced torch downgrade.

**Symptom (second):**
```
ImportError: cannot import name 'to_edge_transform_and_lower' from 'executorch.exir'
```

**Cause:** `executorch==0.3.0` predates the `to_edge_transform_and_lower` convenience API.

**Fix:** Used the lower-level `to_edge()` call available in that version instead.

**Symptom (third):**
```
ImportError: numpy.core.multiarray failed to import
A module that was compiled using NumPy 1.x cannot be run in NumPy 2.2.6
```

**Cause:** ExecuTorch imports `pandas` internally, which imports `pyarrow`. Both were installed as binaries compiled against NumPy 1.x, while the environment had NumPy 2.2.6 installed, an ABI break unrelated to ExecuTorch's own code.

**Fix:** `pip install --force-reinstall --no-deps pandas pyarrow`, rebuilding both against the installed NumPy version.
